# v0.1.1 開發與驗收任務

狀態：已確認並獲授權實作；各任務實際完成狀態如下。

建立日期：2026-11-06。

依據：[Spec](v0.1.1-spec.md)、[增量架構](v0.1.1-architecture.md)、[安全政策](../../SECURITY.md)。本文件不取代 [v0.1.0 任務](../task.md)，避免不同版本的狀態混在一起。

## 1. 範圍與目前基準

沿用 Spec 的 P11-01～P11-05 編號，將錯誤訊息持續／替換／清除、失敗後重試、取消／關閉、版本來源、文件及交付拆成可追蹤工作。不加入 v0.2.0 功能、畫面改版或 p99／500 ms 驗收。

開始規劃時的事實：

- v0.1.0 已發布，保留其 tag、驗收及原始雜湊。
- 安全 workflow、Dependabot、AGENTS.md 規則與 Release security gate 已在 develop；[首次 SAST](../../security/verification.md) 有使用者提供的 Success 證據。
- 安全流程的首次成功不代表 v0.1.1 候選與 tag 已通過，也不能推導平台機密保護／required checks 已啟用。
- 產品仍使用 v0.1.0，新的錯誤快照與版號顯示修正尚未實作。
- 架構與任務文件已確認。確認與同步文件不修改產品、版號、workflow 或發布狀態。

## 2. 狀態與執行原則

| 狀態 | 意義 |
| --- | --- |
| 待開始 | 任務已列出，但尚未執行 |

| 待驗證 | 實作／文件已有結果，仍有必要檢查未完成 |

可一次授權 P11-01～P11-05，依相依順序持續執行，任務編號不是逐項重新詢問的關卡。只有需求／重要設計改變、必要權限或環境缺失時暫停相關工作，其餘已授權工作繼續。

CI、Windows 人工與發布證據分別記錄。失敗、未執行、受阻與通過不得混用；v0.1.0 的結果只能作基準，不能當成本版完成證據。

## 4. P11-01 — 基準與可失敗的重現

**需求對應：** FIX-01～02、AC11-01～03；架構第 2～4、8 節。

工作：

1. 同步 develop，在新工作分支保留既有檔案；記錄來源 commit、SDK、產品版號與現有測試基準。
2. 確認 IP／port 驗證直接寫 Status.Text、Refresh 重新讀 session 的兩條路徑，區分原始碼推論與實際重現。
3. 建立不依賴 WPF 的錯誤／快照測試入口；最小必要重構可以與測試同時進行，但應保留可說明舊行為失敗的紀錄。
4. 案例涵蓋新驗證錯誤被刷新清掉、先有 session 錯誤後產生另一個輸入錯誤，以及修正後有效開始。

完成條件與驗證：

- 可清楚說明修正前為何失敗，有測試或 Windows 重現證據；不能先把預期改成現有錯誤行為再聲稱通過。
- 核心規則以反覆讀取／投影狀態測試，不靠 sleep 三秒；實際 UI 三秒持續顯示另列 P11-04。
- 保存本版實作前的既有 smoke／互通結果；只執行命令或回傳零但沒有案例不算基準通過。

## 5. P11-02 — 統一錯誤來源與恢復

**需求對應：** FIX-01～04、AC11-01～06、SEC-05；架構第 3～5 節。

工作：

1. 由 SimulatorSession 統一保存驗證與背景執行結果；提供一致、不可變的狀態快照及 LastFailure。
2. 在建立 Task／取消來源／socket 前處理無效端點；有效開始被接受時才清除舊錯誤。
3. 協調既有 IPEndPoint 入口與新輸入入口，共用生命週期；不複製另一套 socket 清理流程。
4. MainWindow 改為讀快照顯示；Refresh 不改錯誤，預期失敗不再直接寫一份持續 Status.Text。
5. 分類輸入、設定檔、綁定與執行失敗，提供可理解的說明；不將敏感資料或完整堆疊作為唯一 UI 回饋。
6. 保留取消、停止、關閉與重複開始的保護；不因無效請求取消合法執行中的 session。

完成條件與驗證：

- 新錯誤持續存在、多次刷新不改變；另一錯誤取代舊值，有效啟動後清除；單純編輯欄位或等待不清除。
- 測試缺檔、無效 JSON、重複 OID、被占用端點等錯誤後，可在相同程序修正並成功回應真實 UDP。
- 測試正常取消不成為失敗、停止等待清理、同端點重啟、舊工作不覆蓋新結果，以及執行中重複開始不破壞原狀態。
- 既有 SNMP／JSON 語意、統計與資源上限不變；新增失敗必須診斷，不以刪除 assertion 或停用檢查解決。
- 三專案架構與既有輪詢頻率保留，不新增框架／套件。必要的新相依先依授權與漏洞政策評估。

## 6. P11-03 — 版本與文件一致性

**需求對應：** VER-01、DOC-01、AC11-09；架構第 6 節。

工作：

1. 將集中 Version 設為 0.1.1、AssemblyVersion／FileVersion 設為 0.1.1.0；schemaVersion 維持 1。
2. 視窗由 App 組件取得顯示版本，移除 XAML 與程式碼的固定產品版號；不誤讀 test host／Core 組件。
3. 更新 README、CHANGELOG、本版驗證紀錄；分開寫 v0.1.0 已發布及 v0.1.1 尚未發布，不覆寫歷史文件假造結果。
4. 重要實作差異同步反映架構，重大變更先討論；平台設定與原生元件授權缺證據仍保留未完成。

完成條件與驗證：

- App 組件、檔案與 UI 顯示相符；顯示為 v0.1.1，不含不必要的 commit metadata／第四段。
- 實際建置及版本資訊檢查通過，發版 workflow 可檢查 tag 與 Version 一致；不同版本預期不相符時要失敗。
- 文件連結有效、未發布紀錄如實描述本版變更。版本改變後重新建置，不沿用舊 EXE hash。

## 7. P11-04 — 候選驗證與人工驗收

**需求對應：** AC11-01～09、SEC-01～05；架構第 7～8 節。

工作與證據：

| 類別 | 驗證內容 | 分工與完成條件 |
| --- | --- | --- |
| 本地自動化 | 狀態規則、59 項既有 smoke 的適用案例、真實 UDP、PySNMP 互通 | AI；案例數以實際執行為準，不要求永久固定 59；記錄命令、平台、exit code |
| Windows CI | Windows build and smoke，包含 WPF 編譯、測試、發布及 artifact | AI／GitHub runner；取得當次候選的 run、完整 commit 與結果 |
| SAST | CodeQL C#／WPF、security-extended、SARIF gate | 新候選的 job 成功；高嚴重度或掃描失敗不繞過，不沿用首次安全流程的舊 run |
| SCA | NuGet、runtime packs、Python 完整相依與 advisories | 保留版本及報告，查詢失敗不能當通過，低／中資訊仍需追蹤 |
| 門檻與邊界 | security gate 單元測試、惡意 BER、超限、取消及恢復 | AI；新增錯誤邏輯測試及既有安全案例通過，不宣稱完整 fuzzing |
| 平台防護 | Secret scanning、Push protection、私人回報、required checks | 維護者確認實際啟用及可用方案；若缺權限／方案，記錄限制，不假稱已完成 |
| Windows 人工 | 錯誤至少三秒可讀、最新錯誤替換、修正後恢復、按鈕、關閉、版本 | 使用者；依 AC11-01～06、09 回報，確認是本版 EXE |
| 相容性／內網 | v0.1.0 JSON、七個 OID、v1／v2c 代表性查詢、重載與單檔 | 使用者；依 AC11-08 補驗，沿用 Windows 10 22H2／Windows 11 x64 的支援目標；實際測試環境各自記錄 |

人工驗收使用的產物記錄 SOURCE_COMMIT、EXE SHA-256、OS／build／x64、工具版本與操作。測試舊 JSON 不代表沿用舊 EXE。p99／500 ms 仍為範圍外，不列入失敗或阻擋條件。

AI 無法執行 Windows GUI／跨主機時，先完成自動化與候選，提供具體步驟讓使用者驗收；不要求重做無關的完整手動測試，也不拿交叉建置或 PID 代替驗收。

## 8. P11-05 — 授權與版本交付

**需求對應：** AC11-10、SEC-04、DOC-01；架構第 6～7 節。

工作：

1. 對照實際發布的 runtime／原生元件及相依授權與完整聲明；沒有新 PackageReference 不等於不用核對。若更新相依，核對確切版本與新義務。
2. 彙整本版完成／未完成與驗收證據；授權不明或平台限制先處理，需例外時明確記錄及確認，不自行宣告風險已接受。
3. 依規則 PR 回 develop，候選檢查成功後由 develop PR 回 main；不能由工作分支直接回 main。
4. 確認 main 的發布 commit 與版本，建立 v0.1.1 tag／Release；不移動 v0.1.0 tag。
5. 由 Release workflow 對確切 tag 再做安全檢查、測試、建置與上傳 EXE／ZIP／授權／來源及雜湊。安全 gate 不通過不得上傳。
6. 核對 Release Assets 實際可下載、SOURCE_COMMIT 與 tag 一致、EXE SHA-256 可重算比對；最終改寫 CHANGELOG 為已發布，保留舊版紀錄。

完成條件與驗證：

- PR／合併、tag、Release、同 tag 安全／發布 run 及 artifact 有對應連結與來源。
- 候選與正式 tag 若重建，使用新的 hash，記錄源碼差異並補驗受影響部分；不假定二進位一定相同。
- Actions artifact 存在不等於 Release Assets 已上傳；需在正式 Release 核對下載與內容。
- GitHub API／權限不足時，由使用者在 UI 完成必要操作並回報；記錄未執行項，不直接 push main 或略過規則。
- 合併後的短期分支確認沒有未合併工作才清理；保留 main、develop 與版本 tag。

## 10. 已確認的執行原則

1. 接受沿用 P11-01～P11-05，以重現 → 修正 → 版本／文件 → 候選驗證 → 交付的順序執行。
2. 安全基礎已存在，任務是驗證本版候選及 tag，不重建流程或沿用舊結果冒充通過。
3. Windows 實機、平台設定及跨主機驗收依實際可用環境分工；缺失證據不捏造。
4. 可以一次授權全部任務持續執行；本次產生文件本身不開始產品實作或發布。
