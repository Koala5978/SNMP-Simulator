## 2. 產品目標

建立可在 Windows 執行的視窗式 SNMP Simulator，供 SNMP 查詢工具及監控系統測試設備輪詢行為。

- 使用 C#／.NET 10 LTS。
- 僅支援 x86_64（x64／AMD64），最低作業系統為 Windows 10 22H2（一般版本的最後一個功能更新版本），並支援 Windows 11 x64；ARM64 與 32 位元 x86 不納入。
- 支援 SNMP v1 與 v2c。
- 使用者可攜帶單一 `snmp-simulator.exe` 執行，不需安裝 .NET runtime。
- v0.1.0 同時只模擬一台設備，以少量 OID 正確收送與回應為優先。
- 長期希望承受大量同時請求及回應，採用 p99 往返延遲作為主要延遲指標，暫定方向為 p99 低於 500 ms；此數值不是 v0.1.0 驗收門檻，效能量測方式見第 8 節。

## 3. v0.1.0 使用流程

1. 開啟 EXE，使用內建範例，或選擇外部設備 JSON 設定檔。
2. 設定本機 IPv4 位址及 UDP port。
3. 按下「開始模擬」；程式先驗證資料，成功綁定位址後才顯示模擬中。
4. 外部 SNMP 工具送出請求，程式依載入的設備資料回應。
5. 使用者可觀察累計收送狀態，並停止模擬。
6. 修改設定檔後，停止並重新開始，才套用新內容。

### 4.1 執行與視窗

| 編號 | 需求與驗收條件 |

| RUN-02 | 發布成可獨立執行的 `snmp-simulator.exe`；在未安裝 .NET 的目標 Windows 環境也能啟動。外部 JSON 為選用資料，不是啟動必要檔案。 |

### 4.2 模擬設備與設定檔

| 編號 | 需求與驗收條件 |
| --- | --- |
| DATA-01 | 同一時間模擬一台設備，使用一組監聽 IP／port。 |
| DATA-02 | 提供內建範例，不需準備檔案即可開始模擬；亦可載入外部 JSON。 |
| DATA-03 | JSON 使用 `schemaVersion`、設備 `name`、`community` 與 `objects`。每個物件具有完整數字 `oid`、明確 `type`，固定資料另有 `value`。目前 schema 版本為 1，與程式版本獨立管理。 |
| DATA-04 | 支援固定值型別：`OctetString`（UTF-8 文字）、`Integer32`、`ObjectIdentifier`、`Counter32`、`Gauge32`、`TimeTicks`。數值不得超過對應 SNMP 型別範圍。 |
| DATA-05 | 支援動態 `Uptime`：不需 value，在 SNMP 中編碼為 TimeTicks，從每次開始模擬起以百分之一秒計時，按 32 位元無號值溢位；重新啟動模擬後重設。 |
| DATA-06 | 啟動前驗證必要欄位、schema 版本、OID 格式與重複、型別及值。不合法時不啟動 listener，並提供可理解的錯誤訊息。 |
| DATA-07 | OID 使用完整實例名稱；純量通常包含結尾 `.0`。不要求設定檔預先排序，查詢順序採 OID 數字順序，例如 `.2` 排在 `.10` 前面。 |
| DATA-08 | 開始模擬時一次載入資料；請求處理不逐筆讀取設定檔。執行期間的檔案修改不立即影響回應，重新開始才套用。 |

欄位示例與實際資料見 [samples/device.json](../samples/device.json)。第一版不需要複雜 table 語法；需要時可逐項列出完整實例 OID。

### 4.4 SNMP 行為

| 編號 | 需求與驗收條件 |
| --- | --- |
| SNMP-01 | 使用 UDP／IPv4，同一 listener 接受 v1 與 v2c，依請求版本回應，保留對應 request-id。 |
| SNMP-02 | GET 回應設定的型別與值，支援同一請求內多個 varbind。 |
| SNMP-03 | GETNEXT 回應下一個數字順序較大的 OID；可供外部工具 walk，並正確表示資料結束。 |
| SNMP-04 | v2c GETBULK 處理 non-repeaters、max-repetitions 與資料結束；v1 不接受 GETBULK。 |
| SNMP-05 | v1 不存在物件／結束時使用 noSuchName 與對應 error-index；v2c 依情境使用 noSuchObject、noSuchInstance 或 endOfMibView。 |
| SNMP-06 | 第一版唯讀。一般非空 SET 請求回傳版本適用的拒絕錯誤，不改變設備資料。 |
| SNMP-07 | v1／v2c 使用同一個設定 community，範例為 `public`。錯誤 community 不回應；不支援版本、操作或無法解析的封包予以丟棄。 |
| SNMP-08 | 設定資源與回應大小保護上限，過大請求／回應不得導致無限制配置或處理。具體上限與超限行為須記錄並驗證，不能將應用程式丟棄誤報為網路丟包。 |

v1／v2c 的 community 為明文機制；本版本用途為可控測試網路。Windows 防火牆與監聽 IP 設定由使用者控制，程式不自動變更防火牆規則。

## 5. v0.1.0 不包含的功能

- 從真實設備執行 SNMP walk 並匯入資料。
- SNMP v3、Trap／Inform、SET 寫入。
- 多設備、多虛擬 IP 的設備管理、IPv6。
- MIB 檔案解析、OID 名稱解析及完整 MIB 模擬。
- GUI 編輯 OID、設定檔熱更新、腳本、隨機資料或自動增長計數器（uptime 除外）。
- 任意二進位 OctetString、Counter64 及完整 walk 匯入格式。
- 已保證的高吞吐量、多核心擴展或全部請求低於 500 ms。

未來預期由本軟體提供真實設備 walk 匯入，但時程、格式與功能另行定義，不納入本版驗收。

### 7.1 GitHub Actions 與人工驗收分工

建議採用 GitHub 託管的 Windows x64 runner 自動驗證，搭配使用者的 Windows 實機驗收。本節僅定義驗證規劃，尚未建立或執行 workflow。

| 驗證項目 | GitHub Windows runner 可處理的範圍 | 仍需另外驗證的部分 |

## 8. 效能需求與後續量測

使用者的長期目標是在路由器不構成瓶頸的內網下，同時承受大量請求及回應，採用 p99 往返延遲觀察表現，暫定方向為低於 500 ms。討論硬體基準為 Intel Core Ultra 7 265K、16 GB RAM、僅執行模擬器；OS 依本產品改為 Windows。

目前沒有確認的每秒成功請求數量門檻。先前對各語言的容量數字僅是討論估算，不能作為本版承諾、測試結果或驗收標準。

### 8.1 延遲指標

使用者已確認採用 p99 作為主要延遲指標。500 ms 為依經驗提出並保留的暫定目標，即 p99 低於 500 ms，不是每筆請求的延遲保證，也不納入 v0.1.0 的驗收門檻。正式效能驗收仍需於壓測階段定義負載、測試時間、逾時設定及可接受的失敗率。

p99 為第 99 百分位延遲：將量到的回應時間排序後，約 99% 的樣本不超過此值。例如 10,000 筆有效回應的 p99 為 80 ms，表示約 9,900 筆回應時間不超過 80 ms，其餘可能較慢。實際百分位取樣算法應在壓測工具中固定並記錄。

若僅對成功回應計算 p99，逾時請求不會自動反映在此數字，因此必須另外報告逾時／未收到有效回應的比例及測試 timeout。不能用低 p99 隱藏大量失敗，也不能把未收到回應直接認定為網路丟包。最大延遲與超過 500 ms 的比例也可一併記錄。

### 8.2 標準參考與測試負載

SNMP 協定規範定義操作語意，沒有提供所有 SNMP simulator 都適用的請求／秒、操作比例、OID 數、測試時長或容許丟包率。後續可引用標準定義與量測方法，但不能把自行選定的數字稱為標準要求。

| 參考 | 適用範圍 | 對本專案的使用方式 |
| --- | --- | --- |
| [RFC 3416 §4.2](https://www.rfc-editor.org/rfc/rfc3416.html#section-4.2) | SNMPv2 GET、GETNEXT、GETBULK 等操作；§4.2.3 定義 GETBULK 參數與回應行為 | 作為協定正確性依據，不提供固定的操作比例、每筆 OID 數或建議 max-repetitions |
| [RFC 5345](https://www.rfc-editor.org/rfc/rfc5345.html) | SNMP 流量量測與 trace 交換格式 | 可供日後分析真實輪詢流量與建立代表性負載時參考，不作為統一的效能合格門檻 |
| [RFC 2544](https://www.rfc-editor.org/rfc/rfc2544.html) | 網路互連設備的基準測試方法，包含吞吐量、延遲、丟幀及突發等量測 | 可參考逐步加載與分開報告指標的思路；它測的是網路設備轉送能力，不能直接套成 SNMP 應用程式的驗收標準 |

本次環境存取 RFC 官方原文受限；以上為參考文件與適用範圍整理，不宣稱已完成原文逐條查核。正式採用特定條文前，應再核對原文。

目前不預設持續流量、突發量、測試時間、逾時／丟包合格率，亦不預設 GET／GETNEXT／GETBULK 比例、每筆 OID 數、回應資料大小或 GETBULK 參數。進入效能階段時，優先確認有無適用的標準化測試方法；若沒有，建立可重現的專案測試案例並明示為專案自訂，而非標準值。

初期可以分開量測不同操作與資料量，避免未經依據的混合比例掩蓋瓶頸；測試案例與判定門檻留待壓測階段確認。

### 8.3 測試環境

Windows 支援範圍已依第 4.1 節定義，不再列為待確認需求。網卡速度、壓測端能力與網路條件目前不設限制或指定門檻，留待實際壓測時記錄；CPU／RAM 討論基準也不代表所有部署環境的最低需求。

每次壓測應記錄實際 Windows 版本／build、CPU／RAM、網卡與鏈路、用戶端及工具版本、網路路徑、資料集和測試參數。此為解讀結果所需的環境描述，不是現在新增的硬體限制；不同條件的成績不可直接當成語言或版本效能差異。

後續應以用戶端成功收到且內容正確的回應數／秒計算有效吞吐量，並量測往返延遲、逾時／丟包、CPU 與記憶體。程式內部處理時間、送出計數或 localhost 測試無法單獨證明端到端目標達成。

使用者已確認 v0.1.0 以可執行、正常接收及回應為優先；不將 500 ms、指定吞吐量或負載壓測設為本版完成門檻。低負載通常有較低延遲，但仍不把預期當成已量測結果。
